# Security notes

What the guardrails rely on, what is still unverified, and the trade-offs we accept. An
item stays under "To verify" until a test on a real host proves it.

## The model (DESIGN.md §6)

Every agent: inside Claude Code's built-in sandbox, Bash is auto-allowed with no internet,
the tailnet, and writes to its working folder and tmp. Outside the sandbox, internet and
writes need a human's permission; reads are free. A command a human approved to run
outside the sandbox keeps everything the agent's user may do on the machine, but not the
lab's own credentials and state, nor a view of the service's processes: it starts in a
process namespace of its own, with those folders and files covered (`policy/confine.py`).
The approval itself is unchanged. Grants widen the sandbox for a while
(or permanently, in `lab.yaml`). There is no command parsing anywhere: a parser that
decides from command text is an arms race: an earlier command classifier yielded about ten
bypasses in one afternoon, and that's why we dropped the approach.

## Verified on a cloud GPU worker (2026-10-17)

Ubuntu 24.04, H100, Claude Code 2.1.302, settings generated by `policy/sandbox.py`, host
prepared by `deploy/worker/setup-sandbox.sh`.

| Check | Result |
|---|---|
| GPU inside the sandbox (`nvidia-smi`, `cuInit`) | works, with the `bwrap-gpu` wrapper |
| Tailnet by MagicDNS name | reachable (`*.<tailnet>` on the allowlist) |
| Tailnet by raw IP | refused: agents must use names |
| Host not on the allowlist | refused without a prompt; the agent sees `host is not on the allow list` |
| Host on the allowlist (a domain grant) | reachable |
| Writes: working folder, `/tmp`, a write grant | allowed |
| Writes anywhere else | refused (read-only filesystem) |
| Raw sockets to the internet | refused |
| `.git/hooks`, `.git/config` of repos existing when a command starts (nested too) | write-protected |
| `systemd-run --user` (start a process outside the sandbox) | refused: `/run` is hidden |

What it took:

1. **AppArmor.** Ubuntu's `bwrap-userns-restrict` profile strips capabilities from
   everything bubblewrap starts, and Claude Code's seccomp helper needs one in a nested
   user namespace. Under that profile the sandbox can't start at all (it fails closed).
   `deploy/worker/apparmor-bwrap` replaces it.
2. **GPU devices.** The sandbox builds a minimal `/dev` with no GPU and has no setting to add
   devices. `deploy/worker/bwrap-gpu`, set as `sandbox.bwrapPath` in managed settings,
   binds the GPU nodes right after `--dev /dev`.
3. **Unix sockets.** CUDA opens a Unix socket in `cuInit`, and the seccomp filter can only
   block Unix sockets wholesale, so `cuInit` failed (304) with it on. GPU agents therefore
   allow Unix sockets (`allowAllUnixSockets`). The sandbox hides all of `/run`
   (`denyRead`) except `/run/nvidia-persistenced`, the one socket CUDA needs.
   **Without hiding `/run` this is a real escape:** with sockets allowed, a sandboxed
   `systemd-run --user touch ~/x` created the file outside the sandbox, through the user's
   systemd manager. Every agent hides `/run`; non-GPU agents keep the seccomp block too.

## Still open

- **Sockets outside `/run`.** With Unix sockets allowed, any socket the agent's user can
  reach outside `/run` is reachable from the sandbox. The services run with a private
  `/tmp` (`PrivateTmp=yes`), so the host's `/tmp` sockets (a tmux server, say) aren't
  visible; sockets elsewhere would be. Never run tmux or other socket servers as an
  agent's user, and keep its user without a lingering systemd user manager (the lab
  creates them that way).
- **Long runs outlive the session, by design.** A run (`start_run`, DESIGN.md §4.2) is
  the agent's command running as its Unix user for hours, outside Claude Code's sandbox:
  full network, and any socket server it starts is reachable from the agent's sandbox
  while it lives. Its lab secrets are hidden from the
  run (`InaccessiblePaths=` on `~/.config/agentic-lab`: the member's Claude seat token, the
  lab tokens), so a careless or injected command can't send them away. The job is held
  to the same filesystem policy as the agent's sandboxed commands (one definition for
  both: it writes only the working folder, /tmp and write grants; the lab's secrets and
  state are hidden), applied by the lab because a run outlives the session. Underneath,
  the unit keeps the home read-only and the secrets hidden, in case the job's mounts were
  ever wrong (docs/long-runs.md). That's why a human approves **each** run: no grant is
  offered, `lab check` refuses one in `lab.yaml`, and the runner ignores any. Review what
  the command runs (a script the agent wrote can do anything that user can). What stays
  in place: the run unit has `NoNewPrivileges` (it can't use the worker's sudo rule to
  start more runs), a private `/tmp`, its own process view (a PID namespace from bwrap, on
  every systemd version; a run that can't get one doesn't start), and the worker's sudo
  rule allows only
  `lab-run-ctl`, which starts or stops `lab-run-<that agent>@r-<12 hex>.service` and
  nothing else (the agent comes from `SUDO_USER`). Inside its sandbox the agent can't use
  sudo or reach systemd (`/run` hidden), so only the worker service starts runs.
  Tested: a run started this way outlives the process that started it, and stops cleanly.
- **The secretary's GitHub identity** (optional) is its service's alone: the token and the
  git setup are in its state folder (`~/.local/state/agentic-lab/github`), which its
  agent's sandbox can't read, and its sandbox doesn't get `github.com`. The service uses
  it only for the config repo: clone, branches, pull requests. It never merges or
  approves; that rests on branch protection on `main` (no bypass for bots or apps). Give it
  a fine-grained token limited to the config repo (Contents and Pull requests, read and
  write). Its commits carry a `Lab-Agent:` trailer, so a shared identity still says which
  agent made the change.
- **Readers** (`readers:` on a host, #43) read agents' working folders and their `tmp`
  through a group (`lab-readers`) and ACLs: the agent's home is traversable by the group
  but everything in it except the working folder is made private, and the agent services
  run with `UMask=0077`, so only the working folder's default ACL lets readers in. They
  never write. What an agent keeps in its working folder (data, results, its
  `ENVIRONMENTS.md`) is visible to them, so don't list people who shouldn't see that
  member's work. On such hosts the agent's `TMPDIR` is `<workdir>/tmp` (stable across
  restarts) instead of the service's private `/tmp`: to verify on a first host that
  Claude Code's own temporary files are fine there.
- **Settings are host-specific.** `~` in generated paths expands on the machine that runs
  the generator, so settings must be generated on the agent's own host.
- **Real workloads**: verified, a worker installed PyTorch from PyPI (a domain grant) and
  trained a model on the H100 inside the sandbox.
- **A command that creates a repo and writes its hooks in one go** isn't protected (the
  protection list is built when a command starts). Harmless in our model: git outside the
  sandbox always needs a human's approval, and hooks run by sandboxed git stay sandboxed.
- **Grants mid-session.** Verified: a running session does *not* pick up a changed
  allowlist. A grant therefore applies by restarting the session with the new settings
  (verified seamless: the agent resumes where it was).
- **Claude Code's own command checks.** Even with the sandbox on, Claude Code asks for
  approval of some Bash commands (`export X=...`, `FOO=bar cmd`, some `python3 -c`, loops
  over variables). The worker's permission callback allows any Bash command that stays in
  the sandbox, since the sandbox confines it anyway (verified: writes outside, unlisted
  hosts and the systemd bus all stay refused). Only commands asking to run *outside* the
  sandbox reach a human. Claude Code also blocks a bare `sleep N` (it suggests a
  background wait instead).

## Accepted trade-offs

- **The cloud's metadata service is closed to every lab user** (`169.254.169.254`, and
  AWS's IPv6 address): the host's instance role or service account is never the lab's.
  Every lab unit, and every long run, has `IPAddressDeny` for it (`policy/sandbox.METADATA`),
  which systemd applies to everything the unit starts. It's per unit, not per user: it
  can't tell a service from its own children, which is fine because none of them needs it.
  It relies on cgroup v2 with BPF; `lab doctor` probes it as an agent's user, so a kernel
  that doesn't enforce it shows up as a failure, not a silent pass. A host whose DNS server
  is the metadata address (some GCP images without systemd-resolved) would lose DNS in
  every lab unit: `lab doctor` fails there. AWS and Nebius hosts resolve elsewhere.

- **A member's own keys are readable by their agents** (`member_env.py`): by design,
  since the agent's commands and runs must use them (`WANDB_API_KEY`...). Bounded by: only
  that member's dedicated agents get them (never a shared agent, whose tasks are other
  members'); a key gives no network access, so sandboxed commands still reach only allowed
  sites; long runs have no network limit, but each run is approved by the member. A
  prompt-injected agent could still misuse a key on the service it's for, so members
  should give the lab a key of its own, scoped and revocable, not a personal one. Values
  only ever come through the intake; the secretary shows names, never values.

- **A newcomer being onboarded talks to the secretary before they're in lab.yaml**
  (`secretary/onboarding.py`, DESIGN.md §4.5). Only someone an admin named on the console
  (`lab onboarding start`, as the secretary's user), by Slack member ID; until it finishes
  or is stopped. Their session has no built-in tools (`tools: []`), no lab tools and no
  lab state (the deployed layout isn't in their prompts): only their own checklist, their
  answers (checked in code: a GitHub user name, an SSH *public* key anchored at its type
  so no `authorized_keys` options get in, a manager name), and one-time links for their
  own Claude token and the keys the lab's config lists, stored under their future id. The
  Home tab and buttons stay members-only. What a prompt injection gets them: a chat with
  the secretary on its seat (an admin stops it), nothing of the lab. When it ends their DM
  session is reset, so as a member they start afresh. The intake must be reachable from
  their tailnet login (a policy matter, outside the lab).

- **AWS power uses a stored access key** (#68), an IAM user's, limited to start/stop on
  the lab's tagged instances plus `DescribeInstances` (docs/install.md), never the host's
  instance role: the secretary passes it to boto3 explicitly, with no default credential
  chain, and it lives with the secretary's other secrets, hidden from its agent. A
  long-lived key to rotate (a `credentials` date in lab.yaml); leaked, it can only power
  the lab's own tagged hosts.

- **Local reads are free**, except `/run` and the agent's service's own secrets and state
  (`~/.config/agentic-lab`, `~/.local/state/agentic-lab`): the agent's Read tool is denied
  there and its sandbox hides them; the Claude token is stripped from sandboxed commands.
  Other agents' files are protected by Unix permissions (one user per agent).
- **An agent can read its current GitHub token** (so git and `gh` work). For a bot account
  that's its fine-grained token; for a GitHub App, an installation token that expires
  within the hour (the app's private key stays with the agent's service, out of the
  agent's reach). Safety comes from GitHub: private repositories, permissions limited to
  the lab's repos, and branch protection (human code owners, no bypass for bots or apps),
  so neither can approve or merge.
- **Guests run on the owner's seat**: a member talking to someone else's dedicated manager
  uses that manager's member's Claude seat. Guests get no tools and 2-minute turns (enforced
  in code), so it stays small. In the owner's thread a guest's turn runs in a session of
  its own, built from what the thread shows: it can't draw on the owner's session (tool
  outputs, files read, task details never posted), and the guest's exchange doesn't enter
  the owner's session except as a short visible "meanwhile" note.
- **Anyone with a login on a lab machine can keep it on** (`~/.lab-keep-awake`), which
  costs money while it runs. Visible to everyone in the web UI; an admin (or, on a machine
  dedicated to them, its member) can still power it off (`force_off`).
- **`sudo` on a lab host is admin power**: it reads every agent's files and logs there.
  Give members SSH without `sudo`.
- **The secret intake is open only minutes at a time** (#63): it runs while a one-time
  code is open (5 minutes each), links go only by DM to the person who pastes the secret,
  and it runs hardened; other users' processes aren't visible to it
  (`ProtectProc=invisible`); the secretary's are, since it runs as the same user. A flaw
  in it, while it runs, reaches what the secretary holds within its unit (the secretary's
  state folder, the secrets it handles), and can still read the environments of the
  secretary's processes and signal them.
- **What members see of each other** (#62): the web UI, the Home tab and the secretary
  show a member the lab's state (machines, task states and owners, usage), not other
  members' instructions, results, files or approval details; anonymous tailnet devices and
  lab hosts (agents) only states and counts. With `visibility: team` members see each
  other's work. **On a shared worker this protects against mistakes, not against a
  determined member**: the agent works in one folder, as one Unix user, for every member
  there, so a member can have it copy or link another task's files into their own task's
  folder, which the manager then hands them. The real separation is a Unix user per
  member (or per task); until then, give members who mustn't see each other's work
  dedicated workers.
- **Members' devices are the keys to the logs**: the web UI trusts Tailscale's identity of
  the device (it can't be forged over the tailnet, but a stolen, unlocked laptop is its
  member: an admin's reads every log; a member's, their dedicated agents' logs and their
  own entries of shared ones).
- **Tailnet is trusted.** Any sandboxed command can reach any tailnet host (by name). This
  may tighten to per-host lists as the organisation grows.
- **Allowed domains can carry data out.** A domain grant (say, GitHub) also lets a
  sandboxed command upload there. The docs note domain fronting as a further limit of
  proxy-based filtering.
